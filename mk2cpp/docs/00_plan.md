# mk2cpp 计划（M1–M5，含新增 M4.5）

状态（2026-09-13）：M1–M3 ✅；M4 按“逐指令整理与 stock 28 回归检查点”范围收口
（`97a0ae5`）；**M4.5 原生算法重建待实施**；M5 真 256 复音扩展暂缓。
原 M4 中尚未完成的人类语义目标移交 M4.5，已有代码与证据不回退。
详细目标与收口标准见 [13 M4.5 原生算法重建](13_m45_native_reconstruction.md)。

## 0. 范围

- **终态**：以普通原生 C++ 的算法、数据结构和控制流完整表达 MK2 行为；正常启动、
  复位与播放不依赖 H8/M37450 指令解释、逐 PC 翻译或混合回退。
- **纳入**：主 H8/532 与子 MCU M37450 固件承担的 MIDI、控制、音符、voice、音色、
  参数更新、面板及协作逻辑；与 PCM 声音算法之间的状态和时间契约。
- **复用**：nukeykt 已实现的 PCM 芯片仿真、LCD、RtMidi、SDL、资源加载和其他可用
  设施，以及波形/音色/参数 ROM 数据。PCM 保留为声音基础，以接口与时钟适配接入
  原生控制逻辑；原生化不要求重写设备模型或宿主设施。
- **入口与交付**：同一程序不加 `-mk2cpp` 继续原模拟器路径；加 flag 才进入 M4.5
  原生分支。仍以库集成，不新增 exe，不改默认后端。当前 flag 尚为逐指令翻译入口。
  原版 28 复音兼容与 M5 容量增强分开验收；PCM 滤波配置固定比较，实机差异单独记录。

## 1. 方法与边界

1. **参考执行层（M1–M4）**：`src/gen/` 与 `src/hand/` 保留准确的寄存器、内存、
   标志和指令时序，允许混合回退，以 trace/hash/audio 对照定位固件行为。
2. **原生算法层（M4.5）**：恢复完整算法和状态所有权，逐模块验证后接入原生后端。
   C++ 函数对应完整业务操作，数据字段对应合成器状态；定宽整数与定点按算法保留。
3. **容量增强层（M5）**：在原生状态和声音内核上实现真 256，审计所有读写者、槽号、
   计数、mask、效果槽与时序，保持 stock 28 兼容配置。

迁移期可混合运行以便比较；这只是过渡能力。即使解释器 fallback 为零，只要还在
按 PC 执行生成码/hand 指令函数，也未达到 M4.5 终态。旧 L0 的逐指令状态相同要求
不强加给新的内部表示，原生后端比较映射后的逻辑状态、可观察时序和声音输出。

### M3 子 MCU — ✅ 达成（2026-09-11）
达成记录：
- `smemit`（`tools/h8lift/smemit.c`）：rom_sm 4KB 全译，逐 SM PC 发射 C++（`src/gen/sm/`，
  本地不入 git）。opcode 模型（`sm_op_impl`/`sm_op_len` 表 + 各寻址式表达式）由
  `tools/h8lift/sm_parse.py` 从已入库来源生成：`impl` 取 GT `src/submcu.cpp` 的
  `SM_Opcode_Table`（GT 只实现 165/256），`len` 取 GT handler 路径的取指字节数，
  并逐条与 `tools/disasm/smdasm.c` 的完整 M37450 表交叉校验（165/165 一致），
  非手算；`sm_parse.py --check` 可复验 `smemit.c` 内嵌表。
- 地址模型：SM 固件执行于 `sm.pc ∈ [0xf000,0xffff]`（14 位形式），GT `SM_Read` 经
  `& 0x1fff` 选 ROM、`& 0xfff` 索引，故 smemit 全译该 4096 区间（`g_rom[pc&0xfff]` 仅用于
  解码；发射体调用 GT 运行时 helper，行为与运行期字节无关）。10 个向量目标（reset=0xf003）
  与 VM 校验的 251-PC 执行集全部落在该区间（Python 验证：区间外 0 个）。
- 集成：`mk2cpp.h` 增 `MK2CPP_SM_Register/CanStep/Step` + 统计；`mk2cpp.cpp` 增
  `smk2` 分派表（按 `sm.pc` 索引）；`src/submcu.cpp` `SM_Update` 取指处分派
  （`-mk2cpp` 且已翻译 → `MK2CPP_SM_Step`，否则 `SM_ExecuteOneInstruction` 回退），
  5× 时钟/`cycles+=48`/timer/UART 时序原样不变；CMake 用 `GLOB sm/` + `MK2CPP_HAS_SM_GEN`。
- 验证（`tests/two_mode_check.py`，同一 GT 二进制两模式）：
  - boot [0,3M)：trace 375,116 行（含 125,117 条 `s` 行 SM 指令）两模式逐条一致，
    hashdump SHA256 `91CE3BF8…`（= M1 基线），baseline `trace_boot3m_base.txt` 一致。
  - demo200 [200M,202M)：trace 375,001 行两模式一致，SHA256 `4B445776…`（= M1 基线），
    baseline `trace_200m_base.txt` 一致；hash 含 `hash.sm`/`sm_ram`/`sm_shared_ram`/
    `sm_device_mode`/`hash.lcd_state` 全同 → SM 状态与 LCD 帧序列一致；`sm.cycles≈202M×5`
    印证 5× 时钟。demo200 窗口执行 45 个唯一 SM PC（均在翻译集内）。
oracle：`s` 行 SM trace 与 GT 逐条一致（两模式 + 基线）；LCD 渲染与 GT 相同帧序列
（`hash.lcd_state` 一致）。**已达成。**

### M4 逐指令整理与行为回归（stock 28）— ✅ 检查点收口（2026-09-13）

**范围重划**：保留 `97a0ae5` 已完成的工作，把原定但未完成的“人类可读语义 C++”
移交 M4.5。这里的完成仅指以下检查点，不认定完整算法已恢复。

- hand 已按例程划分与命名，共 27 个 `.cpp`、4239 个 PC 入口；已消除 `case 0x`，
  但主体仍由 `step_*` 操作 `mcu.r[]`、PC 和旧 SRAM 状态。静态 voice 闭包覆盖研究、
  模块边界和原语提取继续作为后续重建的资料。
- 既有 n=28 音频 null 产物与完整状态产物分别一致；提交与本地记录另有指定回归曲、
  boot/定点窗和用户试听通过的说明。独立复核的范围和哈希见 [12 §1.2](12_polyphony_reassessment.md)。
  本次文档更新未重新运行这些测试，也不将历史全量结果算作当前版本的全量验收。
- `MK2CPP_HandBoundary()` 已加入但尚无调用者，hand 没有实际 L1 注册。
  当前 L0 通过不能证明整例程内部的中断与设备服务已得到验证。
- hand 当前无私有运行状态，既有 GT 快照覆盖它；此结论不适用于 M4.5 新增的原生状态。

**现有 M4 工作不回退。** 原解释器、gen、hand、ROM 映射和回归工具保留为参考体系；
新实现按模块对照替换。现有工程可继续运行，M4 检查点有明确的历史边界。

### M4.5 原生算法重建（stock 28）— 待实施

目标：把 MK2 的完整行为与算法恢复成普通 C++ 软件合成器的源码形态，读者无需
模拟 H8/M37450 才能理解程序；先保持原版 28 复音行为。

交付：

- 以完整业务函数与命名字段表达 MIDI/GS、part/音色、note/voice、分配释放、包络/
  音高更新、PCM 参数提交与声音生成；补齐主/子 MCU 协作、面板、启动和复位的依赖。
- 原生状态拥有清晰的生产者/消费者边界与保存恢复机制；声音内核由逻辑事件及音频
  时间直接驱动。原素材离线导入自有 bank，原生全生命周期零原 ROM 文件依赖；
  原寄存器/固件地址映射隔离在研究、导入和迁移适配层。
- 正常运行无需主/子 MCU 指令解释、逐 PC 生成码/hand 分派或隐藏回退。可保留一个
  单独选择的参考后端用于核对；不加 `-mk2cpp` 的原模拟器路径持续保留。
- `-mk2cpp` 分支复用原 PCM 仿真及 LCD/RtMidi/SDL 等设施，只增加必要的控制、数据
  与时钟接入。不加 flag 的回归也是收口条件，共享设施的接线改动不能改变原路径行为。

验收必须同时满足：**算法与源码可读、stock 28 行为等价、原生运行闭包完成**。
零 case、零 fallback、函数改名、单个短窗音频通过都不能独立代替这三项。
参考端使用原 ROM，原生端使用同来源 bank；固定输入/PCM 模式，输出 PCM 逐样本逐 bit
一致，保留必要的定点、截断、饱和和时序。资产与运行隔离验收见 14 §8.1。GT 等价与
MK2 实机滤波还原分开记录，不把已有模型近似算成已解决。

实施顺序：完整小算法样板与时序取证 → 分配/音符关系及 PCM/调度最小链 → 贯通
note 到 voice/PCM 参数链 → 补齐控制、主/子 MCU 行为与启动/复位 → stock 28 全路径收口。
具体边界、验收与迁移约定以 [13 M4.5 规格](13_m45_native_reconstruction.md) 为准。
执行架构见 [14](14_m45_native_architecture.md)，按 [15](15_m45_construction_guide.md)
的 S0–S6 推进：算法契约与隔离测试 → 完整小算法 → 状态/分配关系 → PCM/调度适配 →
发声链 → 冷启动与完整生命周期 → flag 切换收口。各阶段均为待实施。

### M5 真 256 复音扩展 — 暂缓，依赖 M4.5

历史：2026-09-11 的 `pcm_ext_*`、`-voices:`、`0xE800`、page6/7 等扩展已回滚，
当前运行实现仍为 stock 28。旧实验的 255 上限来自哨兵与计数妥协，不是现行能力，
也不是最终验收。`07–11` 保留 ROM 语义证据及旧接口研究，不再规定必须按硬件窗口
补丁路线实施原生扩容。

目标：**256 个可同时活跃的底层发声单元**；多 voice 音色不保证 256 个 MIDI 音符
同时发声。原版 28 复音兼容配置继续可用。

交付与验收：

- **容量**：扩展原生 voice 池、标识与计数、mask、PCM 发声状态及全部读写者，
  正确处理第 256 个 voice，分离无效标识与有效槽号。
- **声音与时序**：保证效果槽隔离，保留每声部算法和更新节奏，明确增强模式混音
  余量/饱和策略；复核 stock 28 回归。
- **边界与性能**：在阶段性容量测试中覆盖超过 28、32、128 到达 256 的边界，
  验证抢音、回收、长时间状态稳定和实时性能。优化须对照正确实现验证。

压力工具在实施时用 Python 3 按新架构补齐，不恢复已删除的旧 `.ps1`。
全量曲库和压力矩阵仍遵循 README 的用户授权与预算规则。本次仅更新路线，未重启 M5。

## 3. 风险与对策

| 风险 | 对策 |
|---|---|
| 只换命名，底层仍执行指令 | 审阅完整操作和调用依赖，检查原生运行路径不执行任何逐 PC 后端 |
| 原状态的读写者遗漏 | 先列出所有生产者/消费者及跨模块边界，再替换布局；未知项明确登记 |
| 时序影响参数与音频 | 恢复事件先后、更新频率和提交规则，用事件/PCM/音频对照验证原生调度 |
| 数值规则被宿主类型意外改变 | 显式保留算法相关位宽、截断、饱和和定点步骤；固定滤波模式比较 |
| GT 已知近似被误算为实机保真 | 重建等价与实机还原分立证据和基线，参见 12 §1.1 |
| 新状态遗漏复位/快照 | 原生状态建立自身保存恢复契约，并验证持续播放与恢复播放一致 |
| 生成物与私有资料入库 | 继续遵循 README/02 的公开文档、生成物和忽略规则 |
| 局部模块完成被当作整个阶段完成 | M4.5 三项门禁全部收口后进入 M5；保留未完成依赖清单 |
