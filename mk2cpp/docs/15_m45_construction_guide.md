# M4.5 施工规程与首个算法样板

## 1. 给施工 agent 的任务说明

> 在现有 Nuked SC-55 中实现 M4.5 原生固件控制后端，继续复用 PCM 芯片仿真、LCD、
> RtMidi、SDL 与资源设施。最终 `-mk2cpp` 选择原生分支，不加 flag 保持原模拟器。
> 原生分支运行零原 ROM 依赖：离线导入原素材为自有 bank，启动至保存恢复均只读取 bank。
> bank 提供标准 WAV 和公开定义，用户可以试听、编辑、替换并重新加载生效，详见 16。
> 未修改原厂 bank 的 stock 28 输出逐 bit 对齐参考；编辑素材按独立功能门禁验证。
> 先做 stock 28，不做 M5 扩容。保留 M4 hand/gen 作为参考，但不让它们成为原生核心
> 的运行依赖。按本文的小切片逐步实施：先写算法契约，再写完整 C++ 算法，再对照验证。
> 不以 PC 覆盖、函数改名、消除 case 或生成一批包装函数作为语义完成证据。

工作以算法为单位，不能按“本轮翻译了多少行 asm”汇报。读 asm 是取证手段；写核心
代码前要能用没有寄存器和地址的语言说清它做了什么。如果还说不清，交付研究结论
和未决问题，并继续其他已明确部分，不用机械转写填充完成度。

不要求每个小步等待用户批准；在已授权范围内依照证据和门禁推进。需要用户参与的
正式试听仍遵循项目既有规则。以下门禁是工程验收，不是额外的人工许可流程。

## 2. 每个切片先写一张算法契约

每张契约同时包含**语义说明**与**证据映射**，前者必须在不打开反汇编时可读。
文件放在本工程 docs 下，具体名称随实际切片确定；不要预生成几十个空文件。

```text
名称与完成状态：例如“stock 28 空闲 voice 队列”，不是“0x19ad 重写”
业务目的：调用者为什么需要它
输入与前置条件：值域、容量、空/满、对象归属、原调用者保证了什么
输出与副作用：返回值、修改的状态、安排的任务、设备读写
算法：自然语言 + 结构化步骤，明确分支、顺序和循环不变量
状态所有权：字段含义、全部生产者/消费者、与其他模块的关系
数值规则：有符号性、截断/回绕/饱和、哨兵转换
时间规则：在哪个逻辑阶段读输入/提交结果，是否能被其他任务观察
证据：ROM/源码版本、例程范围、调用者、消费者、已有 trace/字段依据
未知项：未确认含义/边界以及它阻止哪一项验收
验证：独立预期、参考投影、分支场景、实际命令与结果
范围：这张契约证明了什么；哪些相邻逻辑仍未迁移
```

证据链至少回答“谁提供输入”和“谁使用输出”。只看一个 asm 函数后猜出名字不足以
确认算法。旧 07/11 的表和伪代码也需要按勘误与当前源码核对，不能当作免审的规格。
公开文档不复制 ROM 派生 listing，不写私有素材名称/本机路径；详细运行证据留在本地。

## 4. 首个样板：stock 28 空闲 voice 队列

### 4.1 为什么选它

它小到能完整审阅，又有真实的分配顺序、头尾差异、计数与容量边界；能直接检验施工
是否已经从指令转向算法。它属于 pool-init/分配释放例程族的第一片，不是整个 pool-init。
原 pool-init 还包括其他初始化与中断穿插，不能因为这个纯算法通过就整体替换原例程。

根据 [11 §3](11_slice2_pool_spec.md) 的已有研究与当前 hand，目标关系为：

| 操作 | 语义契约 | 证据定位（仅作映射） |
|---|---|---|
| 初始化 | 空闲顺序 `27 → 26 → … → 0`；head=27、tail=0、count=28 | pool-init 的 free 链构建段 |
| 取出 | 从 head 取一项；数量减一；最后一项取出后 head/tail 均无效 | `pool_pop`，原入口 `0x19ad` |
| 归还尾部 | 非空接到 tail 后；空队列同时建立 head；设置新 tail | release A 与 cleanup 中的队列片段 |
| 归还头部 | 接到原 head 前；空队列同时建立 tail | release B 中的队列片段 |

原状态映射只放参考投影器：`a3d8` 为 next、`a42f/a430` 为 head/tail、`a42d` 为数量。
新核心持有类型化 ID、链和计数；没有 `MCU_Read/Write`、寄存器或 PC。

`takeFront()` 的原有效调用域是已确认非空的队列。核心可用前置条件断言表达；
不得从这个局部接口擅自推出原分配器“空时返回失败/抢最老声部”的完整行为。
归还的 voice 必须有效且尚不在空闲队列中，由调用者契约保证并在测试/诊断中检查。

### 4.2 预期的 C++ 形态

下面展示两个**完整算法体**，成员与 ID 类型按 14 的接口约定定义。它是表达样板，
不是已接入的运行代码；证据映射写在契约中，不塞进每一行算法。

```cpp
void FreeVoiceQueue::initializeStock()
{
    for (uint16_t i = 0; i < kStockVoiceCount; ++i) {
        next_[i] = i == 0 ? VoiceId::invalid()
                          : VoiceId{static_cast<uint16_t>(i - 1)};
    }
    head_ = VoiceId{kStockVoiceCount - 1};
    tail_ = VoiceId{0};
    count_ = kStockVoiceCount;
}

VoiceId FreeVoiceQueue::takeFront()
{
    assert(count_ != 0);
    const VoiceId voice = head_;
    head_ = next_[voice.index()];
    --count_;
    if (count_ == 0) {
        tail_ = VoiceId::invalid();
    }
    return voice;
}
```

这里 `initializeStock()` 的循环说明链如何构成，`takeFront()` 说明首项如何移除。
没有 H8 进位标志，也没有函数之间的 PC 接力。短小的 `VoiceId::invalid()`、`index()`
等类型 helper 合理存在；反对的是逐指令包装，不是所有短函数。

归还头/尾两个算法也要直接表达链表操作。不要把两者合并成默认一种顺序；原分配次序
会决定后续使用哪个 PCM 槽。`std::vector::pop_back()` 并不是天然等价的替代。

### 4.3 必须通过的样板验证

1. 初始化后遍历链恰好得到 27..0，每项一次，tail=0、count=28。
2. 连续取出 28 次得到相同顺序；最后 head/tail 无效、count=0，不出现回绕。
3. 取出 27、26 后，归还 27 到尾部，再归还 26 到头部，链必须为
   `26 → 25 → … → 0 → 27`；计数与首尾一致。
4. 空队列归还、单项取出、头/尾交错归还分别覆盖；约定边界处检查无环、无重复、
   计数等于可达节点数。断言放在业务操作完成边界，不要求原指令中间态也满足它。
5. 使用参考状态投影，对照有效调用域内上述操作的链与数量；独立预期不能仅调用
   被测实现计算。参考投影测试至少能发现头尾颠倒或漏减计数。

样板不涉及 PCM、全局复位、part 计数、`a34c`、H1/H2 链维护或抢音策略，不能把
这些未做的内容记为 PASS。S2 再恢复完整生产者/消费者和设备动作。

## 5. 如何从 asm 得到算法，而不重新造一个虚拟机

实际工作顺序：

1. **追入口和出口**：识别参数、调用者保证、返回值及可见副作用，不沿着地址顺序
   直接写 C++。先确认例程究竟在分配还是释放，避免重复 M4 前的命名误判。
2. **恢复数据流**：寄存器的临时值改写成它所表达的值，如所需 voice 数、空闲数量、
   当前描述符。不要给八个寄存器统一换八个业务名字后继续全程复用。
3. **恢复控制结构**：把计数回边恢复为循环，把条件跳转恢复为条件及早返回；保留
   有意义的遍历方向与原比较规则。结构化之后仍需核对所有路径，而非只看已执行路径。
4. **分开算法与设备**：先计算有意义的结果，显式列出何时读取/提交设备；只有有
   证据的不可观察区间才能整体处理，不在每条算术后补一个伪指令周期。
5. **解释原来的怪行为**：如不寻常的初值、饱和或链顺序，先保留并标来源。不能为
   “现代 C++ 风格”擅自修复固件行为，也不能给未知字段编造解释。
6. **独立核对**：原生代码形成后，再对照原数据流、输入域和事件边界查遗漏；
   不把最终实现重新拆成逐指令函数来换取 trace 一致。

允许在测试/研究中执行原例程获得输入输出，但正常生产核心不得调用它来补未理解
的分支。不得用冻结 trace、预录 MIDI→PCM 写序列或运行时 asm 解码器作为实现。

## 6. 可读性审阅：出现什么就不能通过

以下审阅独立于音频回归，二者必须同时通过。

| 不通过的情况 | 需要补做的工作 |
|---|---|
| `VoiceAllocator` 内部仍执行 `r[8]`、SR、PC 或通用内存地址操作 | 恢复数据含义与完整算法，旧表示移到参考层 |
| 函数名是业务名，主体仍是一串 opcode helper | 重建控制结构和数据流；不能把名字当语义 |
| scheduler 的 task/phase 一对一对应基本块或指令地址 | 找到真正的业务阶段及外部可观察边界 |
| 大量 `unknown_XX`/`f_0xNN` 进入核心并被当成已理解字段 | 记录未知含义与影响，完成相关证据后才能收口 |
| 所有算法集中在巨大 `NativeEngine::run()` | 按状态所有权拆出完整操作，保持调用关系可读 |
| 直接改 `pcm.ram1` 来避开总线协议 | 经 PCM port 保留 latch/read/IRQ 语义 |
| 纯算法测试通过，但仍必须把状态双写 SRAM 才能运行 | 完成边界读写者迁移，双写仅保留在显式过渡适配 |
| 以现代默认规则替换未确认的配对/抢音/包络行为 | 恢复 MK2 原规则，提供输入输出及分支证据 |

自动检查拟覆盖核心 include/链接依赖、PC/寄存器执行入口引用与 native 路径实际命中。
检查不能只搜索 `case` 或 `0x`，也不能因为换了标识符就放行。人或施工 agent 的审阅
必须能回答：这个函数为何调用、读取什么、改变什么、如何分支、结果何时生效。

编译隔离可以证明没有直接链接参考执行器；运行诊断补充确认原生分支未从宿主侧
间接触发 H8/SM/gen/hand。两种证据都不能代替算法审阅。

## 7. 每次交付与最终验收

每个切片提交说明统一记录：

- 已恢复的完整操作和已证实语义，实际源码与契约文件。
- 使用/新增状态的所有读写者；是否还依赖测试导入、过渡桥或未恢复任务。
- 设备与时序处理到哪一步；不能只给 `audio MATCH` 而没有运行模式。
- bank 的来源/导入版本、已覆盖的数据表、数据等价结果及是否仍需原 ROM 文件。
- 透明目录/WAV 到哪一步；原厂兼容与用户替换的实际播放源、失效规则和分开的验证结果。
- 实际验证命令、配置、版本与结果；未运行、SKIP、人工未验收分别标明。
- 下一片的具体未决项，不用“基本完成、剩一些边角”代替清单。

M4.5 最终验收同时要求：

1. S1–S5 的全部运行依赖闭合，核心能作为合成器算法阅读。
2. `-mk2cpp` 自身启动、播放、控制、面板、复位和保存恢复完整，不执行 H8/SM 指令、
   gen/hand 或隐藏回退；正常使用不依赖预热旧快照。原 ROM 不可访问的独立测试环境
   仅提供程序、宿主依赖、bank 与输入，调用和文件访问诊断证明零原 ROM 运行依赖。
3. 继续使用现有 PCM/LCD/RtMidi/SDL；未修改原厂 bank 数据等价、固定配置 stock 28 的事件对照及
   输出 PCM 逐样本逐 bit 一致通过，不得自动移动时间轴或放宽精度；条件见 14 §8.1。
4. 无 flag 分支保持原行为，共享设施的改动通过对应回归。
5. 测试输入覆盖被恢复的关键分支，既有回归曲通过，正式试听有用户在场结果。
   不因本规格自行扩大到全量曲库或 M5 压力矩阵。
6. 按 16 §6 完成公开采样定义、WAV 独立试听/编辑/替换实际生效、派生缓存失效、
   自定义源音高/循环/控制/快照验证，原厂 bit gate 保持独立且持续通过。

未恢复时序或未理解的必要字段是真正的未完成项。不能改名为“适配层”就从验收范围
消失，也不能用零 fallback、零 case、4239 个入口或函数数量宣布里程碑完成。
